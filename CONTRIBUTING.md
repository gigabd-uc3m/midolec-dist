# Contributing

This repository is used to distribute Midolec runtime packages, scripts,
examples, and user-facing documentation.

## Branch Protection

The `main` branch is protected. Changes should be proposed through a pull
request before merging.

Current repository rules include:

- Pull requests are required before merging into `main`.
- Force pushes to protected branches are blocked.
- Deleting protected branches is restricted.
- Repository administrators may have maintenance bypass permissions.

If you are unsure how to prepare a commit or pull request, contact:

```text
gigabd@uc3m.es
```

Use this subject prefix:

```text
[midolec-dist] [git]
```

## Commit Message Format

Start every commit message with the affected Midolec version and a second scope
label.

Recommended format:

```text
[v6] [docs] Clarify installation steps
[v6] [provisioning] Improve runtime installer feedback
[v6] [fix] Rebuild binary with missing runtime archive
[v7] [examples] Add sample execution texts
```

Recommended version labels:

- `[v4.2]` for legacy V4.2 distribution changes.
- `[v6]` for current V6 distribution changes.
- `[v7]` for V7 preparation changes.

Recommended scope labels:

- `[docs]` for Markdown documentation and guides.
- `[provisioning]` for installation, doctor, and runtime scripts.
- `[fix]` for bug fixes, broken packages, or binary reconstruction fixes.
- `[runtime]` for runtime layout, assets metadata, or dependency behavior.
- `[binary]` for executable package updates.
- `[examples]` for sample input texts.
- `[security]` for security policy or vulnerability-response changes.
- `[release]` for release notes, tags, or publication metadata.

## What Belongs In Git

- Configuration files that users may edit.
- Documentation and guides.
- Provisioning scripts.
- Small examples and metadata files.
- Checksums and release notes.
- The current internal packaged workspace while collaborator testing uses this
  repository.

## What Does Not Belong In Git

- FreeLing native libraries.
- FreeLing linguistic resources.
- Downloaded spaCy models.
- Generated JSON outputs.
- Local logs, temporary files, caches, and personal environment files.

Heavy runtime assets should be attached to versioned GitHub Releases or
generated by provisioning scripts.

## Pull Request Checklist

Before requesting review:

- Run the relevant installer or doctor command when changing provisioning.
- Confirm generated JSON files are not committed.
- Keep documentation and command examples aligned with the current scripts.
- Mention the tested environment, for example Ubuntu or WSL Ubuntu.
- Keep unrelated formatting or cleanup out of functional changes.
